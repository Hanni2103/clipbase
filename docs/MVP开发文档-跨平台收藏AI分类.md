# 跨平台内容收藏 + AI 分类知识库 —— MVP 开发文档

## 1. 产品一句话

用户在任何 App（抖音、小红书、公众号、浏览器…）看到想收藏的内容，点「分享」→ 选本工具 → **一键完成，无需任何额外输入**。AI 自动识别分享来的是什么内容、归入分类、打标签，形成个人知识库。

---

## 2. 核心用户流程（一键，零手动）

```
用户在 抖音 / 小红书 / 公众号 / 浏览器 点「分享」
   → 系统分享面板出现，选择本 App
   → App 后台自动完成（用户不再有任何操作）：
        ① 识别收到的是什么（链接 / 文字 / 图片 / 视频文件）
        ② 提取可读的「文本原料」
        ③ AI 分类 + 打标签 + 摘要
        ④ 存库（链接 + 分类 + 标签 + 摘要 + 来源 + 时间）
   → 用户回到 App 看到已归档好的内容
```

---

## 3. 【核心】AI 如何知道用户分享来的是什么内容，并准确分类

这是整份文档的重点。拆成四步，每一步讲清「AI 拿到了什么、怎么判断」。

### 3.1 第一步：接收 —— 系统分享面板给了什么

| 系统 | 分享入口 | 能收到的数据 |
|---|---|---|
| iOS | Share Extension | URL、Text、Image、Video（NSExtensionItem attachments） |
| Android | ACTION_SEND intent | EXTRA_TEXT（文字+链接）、EXTRA_STREAM（图片/视频流） |

关键事实：不同源 App 给的东西不一样。
- 抖音 / 小红书 / 公众号：通常给「标题文字 + 链接」。
- 浏览器：给「链接 + 页面标题」。
- 截图分享：给「图片」。

> 所以「一键完成」是成立的：**分享面板本身已经带了链接和标题**，不需要用户再输入任何东西。

### 3.2 第二步：识别内容形态（「AI 知道是什么」的第一层）

这一层不是靠 AI 猜，而是靠「收到的数据类型 + 链接域名」**确定性路由**，AI 只在兜底时介入。

```
收到分享 → 检查 attachments：
├─ 含 URL
│    └─ 看域名，路由到对应提取器：
│         v.douyin.com / douyin.com      → 抖音提取器
│         xhslink.com / xiaohongshu.com  → 小红书提取器
│         mp.weixin.qq.com               → 公众号提取器
│         b23.tv / bilibili.com          → B站提取器
│         其他域名                        → 通用网页提取器
├─ 只有 Image（无 URL）
│    └─ 走 OCR 提取文字
├─ 只有 Video 文件（无 URL）
│    └─ 抽音频→ASR / 抽帧→OCR（本期后置）
└─ 只有 Text（无 URL 无图片）
     └─ 直接当文字内容
```

### 3.3 第三步：提取「文本原料」（AI 真正要吃的东西）

AI 不直接「看」链接或图片，它**只看文本**。每个提取器把任何输入都归一化成一段干净文本：

| 输入类型 | 提取器动作 | 输出文本（给 AI） |
|---|---|---|
| 公众号 / 通用网页 | HTTP 拉取网页 → readability 抽取正文 | 标题 + 正文 |
| 抖音 | 解析短链跳转 → 读网页上的 title + 文案(description) + 封面 | 标题 + 文案 |
| 小红书 | 解析短链跳转 → 读网页 title + 可见文字 | 标题 + 部分正文 |
| 图片 | OCR 识别图中文字 | OCR 文本 |
| 视频文件 | 抽音频 → 语音转写 ASR（可选：抽帧 OCR） | 转写文本 |
| 纯文字 | 直接用 | 原文 |

> 设计要点：整条流水线的目标是把「五花八门的输入」变成「一段干净文本」。
> **分类准不准，80% 取决于这段文本的质量，20% 取决于提示词。**

### 3.4 第四步：AI 分类 + 打标签（「准确」的关键）

用已备案大模型（DeepSeek / 通义 / 豆包 / Kimi），**结构化输出**，不要自由发挥。

**分类体系（固定封闭集合，MVP 先定 10 类）**：
美食、科技、搞笑娱乐、学习成长、职场、生活方式、健康、财经商业、新闻资讯、其他

**Prompt 设计要点（决定「准」）**：
1. 固定分类集合，禁止 AI 自造分类；
2. 要求结构化 JSON 输出（function calling / JSON mode），字段固定；
3. Few-shot：每个分类给 1~2 个示例，让 AI 对齐你的分类习惯；
4. 优先级声明：「标题 + 文案是主信号，正文是补充」；
5. 输出「置信度」，低于阈值就归「其他」并标记「待确认」，不硬猜。

**输出 Schema（固定）**：
```json
{
  "category": "科技",           // 只能取上面集合里的值
  "tags": ["AI", "效率工具"],    // 3~8 个关键词
  "summary": "一句话说清这篇讲了什么",
  "confidence": 0.92,           // 0~1
  "platform": "抖音"            // 回填，用于后续筛选
}
```

**准确分类的 6 个工程技巧**：
1. 分类体系封闭 + 留「其他」，比开放更准；
2. 结构化输出（JSON schema），别让 AI 写散文；
3. Few-shot 示例对齐习惯；
4. 置信度阈值 + 低置信度降级，避免硬猜；
5. 文本太短 / 为空 → 不分类，标「待补充」（或 OCR 兜底），别让 AI 瞎编；
6. 记录用户手动改分类的行为 → 攒成反馈数据 → 定期回灌到 few-shot，分类越来越贴合个人习惯（这是「准」的长期来源）。

## 4. 技术架构

```
[移动端 App] 分享入口（Share Extension / Intent）
      │ 收到的 payload（URL / Text / Image / Video）
      ▼
[后端 API]  /api/ingest  接收
      │
      ▼
[内容识别层] 类型判断 + 域名路由
      │
      ▼
[提取器层]   网页正文提取 / 短链解析 / OCR / ASR（可插拔）
      │
      ▼
[AI 分类层]  大模型（已备案）→ 结构化输出 分类 / 标签 / 摘要
      │
      ▼
[存储层]   PostgreSQL（元数据）+ 向量库（标签/摘要向量，做语义检索）
      │
      ▼
[客户端展示] 知识库列表 / 分类筛选 / 标签 / 搜索
```

---

## 5. 数据模型（核心表）

```
item（收藏条目）
  id, user_id,
  source_platform（抖音 / 小红书 / 公众号 / 网页 / ...）,
  original_url（链接）,
  title,
  extracted_text（提取文本，仅用于摘要，不对外展示）,
  category, tags[], summary, confidence,
  cover_url（封面，可选）,
  created_at

（可选）tag 表、category 表、user_feedback（用户手动改分类的记录）
```

---

## 6. MVP 范围（做什么 / 不做什么）

**MVP 做：**
- iOS / Android 分享入口（一键）
- 内容识别 + 域名路由
- 提取器：通用网页 / 公众号、抖音、小红书、图片 OCR
- AI 分类打标摘要（结构化输出 + 固定分类）
- 知识库：列表、按分类 / 标签筛选、搜索、点链接回原平台
- 用户可手动改分类 / 标签（既纠错，也攒反馈）

**MVP 不做（后置）：**
- 视频号（技术上浏览器打不开）
- 视频文件的 ASR 转写（用户未直接分享视频文件时可后置）
- 多设备同步、团队协作、公开分享
- 模型微调（先用 few-shot + 反馈回灌，够用）

## 7. 技术栈建议

| 层 | 建议 | 理由 |
|---|---|---|
| App | Flutter 或 React Native | 一套代码两端 + 原生分享扩展 |
| 分享入口 | 原生 Share Extension(iOS) / Intent(Android) | 必须原生 |
| 后端 | Node.js / Go + 队列 | 提取是异步任务 |
| 网页提取 | 服务端 HTTP + readability 类库 | 通用网页 / 公众号 |
| OCR | 云 OCR 或多模态大模型 | 图片文字 |
| 大模型 | DeepSeek / 通义 / 豆包 / Kimi（备案） | 分类打标，JSON 输出 |
| 存储 | PostgreSQL + pgvector | 结构化 + 向量检索 |

---

## 8. 里程碑（建议顺序）

1. **M1（1~2 周）**：iOS / Android 分享入口收到 payload → 后端接收 → 通用网页 + 公众号提取 → AI 分类打标 → 存库 → 列表展示。**先跑通「网页类」这一条完整链路。**
2. **M2（1 周）**：加抖音、小红书短链解析提取器。
3. **M3（1 周）**：图片 OCR 兜底 + 标签筛选 + 搜索。
4. **M4（迭代）**：用户改分类反馈回灌、封面、置信度优化。

---

## 9. 关键技术风险（提前排雷）

| 风险 | 说明 | 应对 |
|---|---|---|
| 抖音/小红书短链解析会命中反爬 | 平台网页对自动化访问有风控，接口/页面结构会变 | 提取器做成可插拔，单独隔离，坏了只影响单一平台 |
| 小红书不登录只能拿到部分文字 | 分类通常够用，但「深度理解」受限 | 标题 + 文案为主信号；拿不到正文就降级为摘要级分类 |
| 分享面板字段因源 App 而异 | 有的 App 只给链接不给标题 | 无标题时用提取器补标题，兜底 OCR |
| 分类准确率初期不够高 | 冷启动没有个人习惯数据 | 用固定分类 + 置信度降级 + 用户可改分类攒反馈 |

---

## 10. 合规底线（一句话版，不再展开）

- 只存「链接 + 摘要 + 标签」，不存原文 / 原视频 / 原图（用户主动分享的截图除外）；
- 用已备案国内大模型；
- ICP 备案 + 隐私政策 + 用户同意 + 可删除；
- 对锁定平台只取「标题 / 文案 / 摘要级」公开信息，不绕登录、不去水印、不下载视频流。
